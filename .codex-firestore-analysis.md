# Firestore analysis notes

- Target: `projects/at-long-last/databases/(default)`, Standard edition, Firestore Native, `nam5`.
- Authentication: Firebase Auth, including anonymous and provider-linked identities.
- Relevant collections: `couples`, `coupleInvites`, `playerCouples`, `sessions`, `publicLobbies`, and nested journal/chat collections.
- Critical transactions: invite creation/join, couple session start, session lifecycle progression, session completion/abandonment with atomic couple pointer updates.
- Reported denied write: participant atomically clears `couples/{coupleId}.activeSessionId` and changes a pre-current-schema `sessions/{sessionId}` from active to abandoned.
- Compatibility constraint: permit only terminal cleanup of historical documents; do not weaken modern create/update validation or invite/join authorization.

## Query and CRUD inventory

- `profiles/{uid}`: owner `set`/merge and exact subscription; private email is never collection-readable.
- `playerCouples/{uid}`: exact owner read/create/update/delete pointer.
- `coupleInvites/{code}`: exact authenticated `get`; create/delete only inside couple lifecycle transactions; listing denied.
- `couples/{coupleId}`: exact participant subscription; transactional create/join/leave/session-pointer updates.
- `publicLobbies`: authenticated collection subscription ordered by `updatedAt desc`; exact transactional create/update/delete.
- `lobbyMessages`: authenticated collection subscription ordered by `createdAt asc`; bounded immutable create.
- `sessions/{sessionId}`: exact participant subscription; transactional create and lifecycle updates; delete denied.
- `activities/{activityId}`: exact participant subscription; bounded create/update; delete denied.
- `journalEntries`: participant query filtered by `coupleId ==` and ordered by `createdAt desc`; immutable create.

## Relevant model constraints

- Couple authority comes from the existing `playerIds`; request data cannot grant participant authority.
- Couple invite identity, creation timestamp, player identity, and session relationship are immutable outside explicit join/leave transitions.
- Modern sessions use the complete arc schema and strict status transitions. Historical pre-arc sessions lack spotlight, momentum, activity-option, and keepsake-perk fields.
- The legacy compatibility validator accepts only an existing participant's atomic `active -> abandoned` transition while the matching couple pointer becomes null.
